023渲染管线：Forward vs Deferred

你写的每个 draw call 背后，引擎都在做选择：先画什么？光照在哪一步算？透明物体怎么处理？这些选择的组合就是渲染管线。Forward 和 Deferred 是两大主流方案，决定了引擎能支持多少灯、多复杂的效果。

核心概念

渲染管线 Render Pipeline

从场景数据到最终像素的完整流程：几何 → 光栅化 → 光照 → 后处理。不同管线的区别在于"光照在哪个阶段算"——这决定了性能特性和效果上限。

Forward Rendering 前向渲染

传统方案：每个物体画一遍，画的时候就算光照。简单直接，但灯多了性能爆炸——每多一盏灯，每个像素都要多算一次。

Deferred Rendering 延迟渲染

现代方案：先把所有几何画到 G-Buffer（位置/法线/颜色/材质参数），再统一做光照。灯多不怕——光照只算一次，和灯数量无关。代价：内存大、透明物体难处理。

Forward：一个物体一个物体画

// Forward 的流程
for 每个物体:
  for 每个像素:
    颜色 = 0
    for 每盏灯:
      颜色 += 计算光照(灯, 像素)  // ← 灯越多，这里越慢
    输出颜色

// 问题：10 盏灯 × 100 个物体 = 1000 次光照计算
优点缺点
简单直观，好调试灯多性能爆炸
透明物体好处理每像素重复算光照
支持 MSAA 抗锯齿无法高效做屏幕空间效果
内存小不适合复杂光照场景
手机平台几乎都是 Forward：灯少（通常 2-4 盏）、透明多（UI/特效）、内存宝贵。Unity URP、Unreal Mobile、Godot Mobile 都是 Forward。

Deferred：先画几何，再统一光照

// Deferred 的流程
// Pass 1：几何 pass，把信息写到 G-Buffer
for 每个物体:
  G-Buffer.位置 = 像素世界位置
  G-Buffer.法线 = 像素法线
  G-Buffer.颜色 = 材质颜色
  G-Buffer.金属度 = 材质金属度
  G-Buffer.粗糙度 = 材质粗糙度

// Pass 2：光照 pass，只算一次
for 每个像素:
  颜色 = 0
  for 每盏灯:
    颜色 += 计算光照(灯, G-Buffer[像素])  // ← 和物体数量无关
  输出颜色
优点缺点
灯多性能稳定G-Buffer 内存大（多通道高分辨率纹理）
光照只算一次，不重复透明物体难处理（G-Buffer 只能存一层）
天然支持屏幕空间效果（SSAO/SSR）不支持 MSAA（G-Buffer 是纹理）
适合复杂光照场景调试困难（看不到中间结果）
Deferred 的透明问题：玻璃、水面、粒子特效——这些透明物体在 Deferred 里要单独走 Forward pass 处理，引擎自动帮你做（Forward+），但性能会退化。所以 Deferred 不是"透明免费"。

现代变体：Forward+ 和 Tile-Based

方案原理解决什么代表
Forward+屏幕分块，每块只算受影响的灯Forward 灯多爆炸Unreal 4/5、Unity URP
Tile-Based Deferred屏幕分块，G-Buffer 也分块，减少内存带宽Deferred 内存大现代主机/PC
Clustered3D 空间分块，视锥内灯可见性更精确的灯剔除UE5、Unity HDRP
Forward+ 是手机平台的未来：分块剔除让 Forward 也能扛住 100+ 盏灯，同时保留透明友好、内存小的优势。Unity URP 和 Unreal Mobile 都在向这个方向演进。

口头描述练习

🗣️ 手游项目的渲染管线选型怎么描述？

"选 Forward+（Unity URP）。原因：手机平台灯少（主平行光+2-4 盏点光）、透明特效多（技能/UI/水面）、内存宝贵（G-Buffer 存不下）。Forward+ 的分块灯剔除让我们在关键场景（主城/副本）也能放 20-30 盏装饰灯。Godot 项目用 Mobile 渲染器——Forward+ 的手机优化版，特性精简但性能最好。Compatibility 只在 Web 版用。不考虑 Deferred：G-Buffer 内存太大，透明处理复杂，手机平台的优势（灯多稳定）我们用不上——我们的灯本来就少。"

→ 你用了平台约束分析（灯少/透明多/内存小）、Forward+ 分块优势、Godot Mobile/Compatibility 分工、Deferred 排除理由。这就是完整的管线选型思路。
